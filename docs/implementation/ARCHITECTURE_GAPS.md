# Architecture Gaps and Conflicts

**Status:** Draft for approval. No implementation has started.
**Baseline:** re-baselined on `specs/specv3.md` (V3). The user ruled that V3 **replaces** `specs/spec.md` and `specs/specv2.md` (D8). `specv2.md` and `specv3.md` are byte-identical.
**Sources:** `specs/specv3.md` (V3), `specs/architect.md` (ARCH), `specs/frontend-spec.md` (FE), `CLAUDE.md`. `spec.md` and `specv2.md` are superseded and kept for history only.
**Precedence:** V3 > ARCH > FE > CLAUDE.md. Where ARCH cites `spec.md` section numbers, read them against V3 and let V3 win.

"Approval" = it changes business behavior, scoring semantics or a public contract, so the affected area must wait.

| D32 | Penalty semantics fixed in phase 5 where V3 leaves them open (object if you disagree): (1) tie-break rank: a lower `priority` number wins, then `ruleOrder`, then penalty id, then version (tie-break version "1"); (2) each policy acts only among penalties declaring that policy, in this order per target: EXCLUSIVE_GROUP (per group, winner by rank), MAX_PER_CATEGORY (per category, largest), MAX (largest), PRIORITY (best rank), then one CAPPED_STACK pool per target filled in rank order up to a cap that all pool members must share; STACK always kept; (3) a candidate rounds to 2 dp after the individual maximum; a zero result is NOT_TRIGGERED (ZERO_DEDUCTION); missing score-base data is INELIGIBLE; a trigger pattern that did not match or is disabled is NOT_TRIGGERED, one that could not be evaluated or is ineligible is INELIGIBLE; (4) a penalty has one trigger pattern id and version; a pattern shared by a dimension penalty and an OVERALL penalty needs a written dual-application rationale on every penalty that uses it; (5) score bases are RAW dimension scores or a raw dimension gap only (no adjusted or weighted LIS base yet). | Implementation |
| D33 | Configuration decisions fixed in phase 10 where V3 leaves them open (object if you disagree): (1) lifecycle transitions: DRAFT to VALIDATING; VALIDATING to DRAFT (failed validation) or ACTIVE; ACTIVE to PAUSED or ARCHIVED; PAUSED to ACTIVE or ARCHIVED; ARCHIVED is final; only DRAFT content is editable; (2) at most one ACTIVE version per configuration slot (database unique index); activating a new version archives the previous one; a paused version cannot resume while another is active; (3) the platform operator manages platform defaults only, a tenant caller manages only its own tenant's layers, and a foreign version id looks like a missing one; (4) a layer (template, organization, tenant) is validated by merging it over the active platform default only; (5) merge: objects merge recursively, scalars and arrays are replaced (no catalog merge by id), `{"$remove": true}` deletes a field, unknown fields are rejected; (6) the configuration document format is the sample in `src/test/resources/sample-config/`; the effective version is a string such as `platform_default:v1|tenant:v2`; the configuration hash is the SHA-256 of the canonical merged document; (7) validation reports the first problem found, not all of them (V3 §30.6 asks for all useful errors; improvement left for later); (8) the effective-configuration cache expires after 5 minutes at the latest, is evicted per tenant (platform changes: all) after commit, and becomes stale at a version's scheduled effective date; (9) activation requires approval metadata; representative fixtures and preview (V3 §23.6) are not implemented because no spec defines them; (10) Testcontainers is pinned to 1.21.4 because 1.21.0 cannot talk to Docker Engine 29. | Implementation |
| D34 | Persistence decisions fixed in phase 11 (object if you disagree): (1) a run is stored with all its findings in one transaction; invalid input to `/calculate` stores nothing; an engine failure on a stored assessment is stored as a FAILED run (error code, no scores, no trace) and is never returned as the latest result; (2) the scoring history tables are immutable (database triggers reject update and delete); retention and deletion are left to a platform policy; (3) "latest run" is the highest sequence number among COMPLETED runs; (4) an idempotency key is bound to its first request in its own table, whether that request created a run or reused one; the same key with a different request is IDEMPOTENCY_CONFLICT; keys are per tenant and kept as long as the run; (5) the V3 §27.4 identity is enforced by a unique index on COMPLETED runs that are not recalculations, so concurrent identical requests produce one run; (6) the explicit configuration of a recalculation is a configuration version id (ACTIVE or ARCHIVED, own tenant or platform), merged over the active platform default; its effective version is written `explicit:...`; (7) organizations and template versions are registered on first use because they arrive with the request (D13); an unknown tenant is TENANT_ACCESS_DENIED; (8) the trace is stored as jsonb and returned as the database returns it (spacing and key order normalised, numbers and content unchanged); child tables hold the queryable findings; `scoring_signal_result` and `scoring_penalty_aggregation` are not separate tables because signals and totals are in the trace; (9) scoring and recalculation audit events (V3 §33.4) are not separate records yet: the run itself is the record. | Implementation |
| D35 | API decisions fixed in phase 12 (object if you disagree): (1) the sub-resource endpoints (`/dimensions`, `/patterns`, `/penalties`, `/imbalances`, `/explanation`) and the main result are shaped from the stored trace, so nothing is recalculated and entities are never serialized; there is no pagination or filtering yet; (2) the VIEWER role receives a redacted copy: no normalization or signal step, no contributions or drivers, no evidence values or condition details, no score-base values; OWNER, ADMIN and ANALYST receive the full trace; (3) every read checks both the tenant (another tenant's id looks like a missing one: 404) and the organization (an organization outside `org_ids`: 403 ORGANIZATION_ACCESS_DENIED); an absent `org_ids` claim means no organization; (4) configuration faults found while scoring are HTTP 500 with the code but without the internal message; unexpected errors are 500 SCORING_EXECUTION_FAILED; only the exception class and correlation id are logged; (5) extension error codes: INVALID_REQUEST (400, 405, 415), UNAUTHENTICATED (401), ACCESS_DENIED (403 for a role that does not allow the operation); (6) `Idempotency-Key` applies to `/calculate` and `/score`; `/recalculate` always creates a run; (7) token verification uses `lis.security.jwk-set-uri`; without it every token is rejected; the OpenAPI document requires a token; actuator health and info are open; (8) request bodies are limited to 1000 answers and 10,000 characters per text answer; a declared `questionType` is checked, never used; (9) `GET /scoring-runs/{id}` of a FAILED run returns status FAILED with the error code and no scores; its sub-resources and explanation return 404. | Implementation |
