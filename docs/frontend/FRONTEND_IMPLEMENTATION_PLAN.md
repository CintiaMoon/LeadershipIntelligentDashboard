## Entry criteria for each phase

- Endpoints it consumes are marked "exists" or "approved" in `API_DEPENDENCIES.md`.
- OpenAPI types generated from the backend, not hand-written.
- No screen is built against an invented endpoint or response field (FE §26.4).

## Cross-cutting tasks

- Typed API client; centralized 400/401/403/404/409/422/429/500/503 handling (FE §16.3).
- TanStack Query keys, stale time, invalidation, retries, pagination; background refresh only if async scoring is introduced (F8).
- Zustand only for selected organization, navigation preferences, global filters, display preferences. Never store canonical scoring results (FE §18).
- Shared states: loading skeletons, empty, error, stale-data banner (FE §18, §20).
- A single `formatScore` helper preserving backend scale; lint rule forbidding arithmetic on score fields outside presentation helpers.
- Mock layer isolated from production API integration (FE §26.9); production build excludes mocks.
- Accessibility: WCAG 2.2 AA; every chart has a textual summary (FE §20).
- Performance targets (FE §23) treated as suggestions to validate.

## Sequencing recommendation

1. Phase 1 scaffolding (no auth): tooling, tokens, layout, API client skeleton.
2. Decisions D11, D19, D20, D24 are recorded in `docs/implementation/ARCHITECTURE_GAPS.md`.
3. Phases 2 (run details), 3, 4 against `/scoring-runs/**`.
4. Phases 5 and 6 only after F5, G1, F13 are specified.
5. Phase 7 continuously (tests) and as a final gate.

## Definition of done (FE §25)

All primary scoring screens implemented; all data from backend; every score traceable; patterns show evidence and confidence; penalties show candidate and effective deductions; suppressed penalties visible with reasons; imbalances distinct from penalties; comparisons respect comparability metadata; role restrictions in UI; loading, empty, error and stale states; responsive and accessible; unit, integration, E2E pass; no scoring logic duplicated.
